# ADR-001 — Transferencias directas y autorizadas a R2

- **Estado:** Aprobado por solicitud explícita del propietario del proyecto el 2026-10-11.
- **Ámbito:** Vega Drive existente; no presupone ni implementa una API externa nueva.
- **Despliegue:** Este ADR no autoriza un despliegue automático. La migración se habilita solo tras pruebas y configuración operativa verificadas.
- **Decisión:** El Worker conserva el plano de control y autorización; los bytes de subida y descarga se transfieren directamente entre navegador y el endpoint S3 compatible de R2 mediante URLs prefirmadas de alcance mínimo y duración corta.
- **Bucket:** Debe permanecer privado, sin dominio público ni `r2.dev`. El acceso directo se permite únicamente mediante solicitudes S3 firmadas. No se permite acceso anónimo.
- **Credenciales:** Las credenciales S3 de R2 se guardan como secretos del Worker, limitadas al bucket `vega-drive-files`, con permisos mínimos de lectura/escritura de objetos. Nunca se entregan al cliente ni se versionan.
- **Origen/CORS:** Configurar CORS de R2 con los orígenes exactos `https://vega-drive.programadorkevinsvega.workers.dev` y `https://drive.jnmtortas.com`, métodos GET/PUT, AllowedHeaders `Content-Type` e `If-None-Match`, y ExposeHeaders `ETag`. No usar `*` ni añadir localhost al bucket de producción. CORS no es autorización; la firma y la autorización del Worker son obligatorias.
- **Subidas pequeñas:** El Worker valida sesión, carpeta, nombre, tipo declarado, tamaño, cuota y límites de uso; reserva cuota de forma atómica y genera una clave aleatoria de servidor. Emite una URL PUT prefirmada para un único objeto, con expiración breve, Content-Type firmado e `If-None-Match: *` para rechazar PUT cuando el objeto ya existe; esta condición no se considera un bloqueo atómico frente a carreras simultáneas; después el Worker verifica el objeto mediante HEAD y solo entonces publica metadatos.
- **Subidas grandes:** El Worker crea y conserva en D1 la sesión y la reserva de cuota; inicia multipart por S3; emite URLs prefirmadas para números de parte válidos y solo para esa sesión/clave. El navegador sube partes directamente. Cada URL contiene solo los parámetros firmados de esa parte; el ID S3 no se devuelve como campo independiente. El Worker valida la lista de partes contra la sesión y completa el multipart; después verifica HEAD/tamaño antes de marcar el archivo disponible. La sesión pertenece al actor autenticado, expira, puede abortarse y se limpia automáticamente.
- **Descargas:** El Worker resuelve el ID lógico en D1, comprueba propiedad, estado activo y permisos; solo entonces emite una URL GET prefirmada para la clave exacta, con vida corta y respuesta de descarga segura. No se aceptan claves de R2 enviadas por el cliente.
- **Permisos/revocación:** Una URL prefirmada es una credencial portadora temporal y puede usarse hasta expirar. No se afirma revocación instantánea de URLs ya emitidas. Para operaciones sensibles, la expiración será mínima; el borrado puede eliminar el objeto y las sesiones pueden invalidarse en D1, pero una URL GET ya emitida no puede considerarse revocada hasta que expire o falle el acceso al objeto.
- **Cuotas y concurrencia:** La reserva de capacidad se serializa en D1 antes de emitir URL alguna. Las finalizaciones son idempotentes y verifican tamaño real, estado de sesión, propiedad y expiración. Se aplican límites por usuario/IP, sesiones simultáneas y frecuencia.
- **Frontend:** Puede recibir únicamente URLs de operación prefirmadas y temporales. La URL contiene el endpoint y la ruta/parte fijados por el servidor como parte de la firma, pero no entrega credenciales ni permite escoger o modificar el objeto, método o expiración. Las URL y parámetros sensibles no se guardan en localStorage, no se registran en logs y se mantienen fuera de analítica.
- **Compatibilidad:** La API same-origin sigue siendo el plano de control para iniciar, autorizar partes, completar, cancelar y descargar/autorización. El flujo de transferencia antiguo permanece disponible como rollback hasta que el nuevo flujo supere E2E y pruebas de seguridad/carga.
- **Condiciones para activar:** Confirmar cuenta/endpoint R2, configurar secretos fuera del repositorio, CORS exacto, permisos mínimos, tests de aislamiento y expiración, pruebas de archivos grandes/reanudación/cancelación, auditoría de cuota y pruebas concurrentes; luego habilitar mediante feature flag. No activar ni desplegar sin autorización explícita.
- **Pruebas obligatorias:** Acceso cruzado entre usuarios; URL expirada; método, objeto, encabezados y parte alterados; sesión abortada/expirada; replay; cuota concurrente; objeto con tamaño incorrecto; ETag faltante/alterado; intento de completar una sesión ajena; descarga de archivo en papelera; CORS no autorizado; rollback.
- **Riesgo aceptado y mitigación:** R2 documenta soporte para `If-None-Match` en `PutObject`, pero no se asume garantía atómica frente a escrituras condicionales concurrentes. Las claves aleatorias de servidor y la autorización por sesión son obligatorias. Las URLs firmadas son credenciales portadoras. Se limitan a una sola acción/objeto/parte, expiración corta, permisos S3 mínimos y ausencia de logging. CORS solo controla navegadores y no reemplaza la firma.
- **Conflictos documentales:** Este ADR sustituye únicamente las reglas previas que prohíben todas las URLs prefirmadas o cualquier acceso de navegador a R2. Todas las demás reglas de aislamiento, privacidad, cuota, límites modulares, cabeceras y secretos siguen vigentes.
